# 异步 Swap 过度抢占修复报告

## 问题

在 24 个 GPU KV block 的压力配置下，完全异步方案出现 22 次 block
换出和 22 次换入，而同步方案只有 8 次。完全异步方案的吞吐比同步方案低
12.97%，TPOT P95 高 16.18%。

正确性 trace 表明，22 次 block 传输来自 11 个请求各换出一次，每个请求占用
2 个 block。它不是同一请求反复换入和换出的抖动。

## 排除的假设

我们先试验了“请求换入后至少驻留 4 或 8 个生成 token”的策略。三个阈值的
换入/换出次数均为 22/22，调度步数均为 145，强制打破驻留保护的次数为 0。
因此最小驻留时间没有命中实际问题，这部分试验代码没有保留在生产路径中。

## 根因

异步 D2H 提交后，victim 的 GPU block 必须等 CUDA event 完成才能释放。在旧的
decode 调度循环中，只要当前请求无法追加 block 且 running 队列仍有请求，调度器
就继续选择下一个 victim。检查 `swapping_out` 的分支位于选择 victim 之后，因而
同一轮会在第一批 block 尚未释放时连续驱逐请求。

同步路径会立即得到已释放的 block，所以不会形成这次驱逐波。这也解释了为什么
问题只在异步路径明显出现。

## 修复

当已有 D2H 换出尚未完成时，无法追加 block 的请求先回到 running 队列等待。调度器
在事件完成、GPU block 真正回收之后重新判断容量，只有仍然缺少空间时才选择新的
victim。

该规则没有假定传输时长，也没有忙等待 CUDA event。它只把抢占决策推迟到调度器
拥有真实可用 block 数量的时刻。

## 实验设置

- 单张 NVIDIA A800 80GB PCIe
- Qwen3-1.7B，本地权重
- 12 个请求，输入 512 token，输出 64 token
- 24 个 GPU KV block，CPU swap 空间 4 GiB
- argmax 采样
- 每种方案运行 3 个独立进程，轮换执行顺序

原始结果保存在本地忽略目录，仓库只保存汇总结论。

## 修复前后结果

| 指标 | 同步（修复后复测） | 安全异步（修复前） | 安全异步（修复后） | 完全异步（修复前） | 完全异步（修复后） |
| --- | ---: | ---: | ---: | ---: | ---: |
| 吞吐（tok/s） | 198.076 | 196.729 | 196.660 | 170.933 | 196.653 |
| TTFT P95（ms） | 332.021 | 331.607 | 328.339 | 334.761 | 331.415 |
| TPOT P95（ms） | 56.752 | 57.176 | 56.816 | 66.483 | 56.773 |
| 换出 block | 8 | 12 | 8 | 22 | 8 |
| 换入 block | 8 | 12 | 8 | 22 | 8 |
| 调度步数 | 138 | 140 | 141 | 145 | 142 |

修复后，完全异步相对同步的吞吐差距为 -0.72%，TTFT P95 为 -0.18%，TPOT
P95 为 +0.04%。完全异步的吞吐损失从 12.97% 收敛到测量波动附近。

安全异步与完全异步的输出均有 10/12 个请求与同轮同步结果逐 token 完全一致。
此前的 logits 追踪已经确认差异来自 BF16 数值轨迹和 argmax 边界，不存在读取仍在
换出的 GPU block 的情况。因此这里不把逐 token 完全一致作为异步传输正确性的唯一
判断依据。

## 验证

- 14 个 CPU 调度回归测试通过，其中新增用例验证 pending D2H 期间同一轮只选择一个 victim。
- 2 个真实 CUDA event 集成测试通过。
- 单次 correctness trace 中，完全异步换入/换出从 22/22 降到 8/8。
- 三方案各 3 次独立进程的正式复测中，安全异步和完全异步都稳定为 8/8。

## 结论

异步传输改变了资源释放的时刻，调度器不能把“已发起释放”当成“已经可用”。这次
优化的收益来自消除错误的额外工作，而不是让 memcpy 本身更快。修复后完全异步方案
恢复到与同步方案接近的吞吐和 TPOT，同时保留 D2H/H2D 与计算重叠的实验能力。
