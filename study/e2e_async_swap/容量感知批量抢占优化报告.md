# 容量感知批量抢占优化报告

## 项目摘要

本项目针对 LLM 推理服务中的 KV cache GPU/CPU offload，分析并优化异步 swap 在高并发
场景下的吞吐退化。系统已经使用独立 CUDA stream 和 `cudaMemcpy2DAsync` 重叠 KV
传输与模型计算，但原异步调度器每次只换出一个请求，导致 GPU 内存压力出现时形成多轮
小批次 decode。

本次实现容量感知的批量抢占：调度器根据下一轮 decode 的 block 需求和 victim 可释放
容量，一次选择刚好足够的 victim，并用一次 D2H batch 提交。最大压力消融实验中，完全
异步吞吐从 363.442 提升到 388.255 tok/s，提升 6.83%；相对同步从 -6.20% 提升到
+0.21%，请求输出匹配从 17/24 恢复到 24/24。

## 背景

LLM decode 每生成一个 token，都要读取历史 KV cache。当 GPU KV 空间不足时，系统可以
把部分请求的 KV blocks 换出到 pinned CPU memory，稍后再换入。同步 swap 会阻塞模型
执行；异步 swap 可以使用 copy engine 与计算重叠，但也把 block 的释放从“立即完成”
变成“CUDA event 完成后生效”。

项目此前已经完成：

1. GPU/CPU block 生命周期和 swapped 队列实现。
2. `cudaMemcpy2DAsync` 与独立 swap stream。
3. `SWAPPING_OUT`、`SWAPPING_IN` 和 CUDA event 状态机。
4. pending D2H block 禁止提前复用。
5. 修复同一轮在未知可用容量时驱逐过多请求的问题。

上一版为了保证安全，在 pending D2H 时停止选择更多 victim。这消除了过度驱逐，但使
异步调度器退化为每轮只换出一个请求。

## 基线问题

在 24 并发、输入 1024 token、输出 128 token、96 个 GPU KV blocks 的场景中，每个
block 为 28 MiB，单方向共交换 20 个 blocks，即 560 MiB。

旧串行异步策略的行为是：

```text
选择 1 个 victim
→ 提交 D2H
→ 等待 event
→ 回收 GPU blocks
→ 调度一小批 decode
→ 仍然缺空间，再选择下一个 victim
```

同步调度器可以在一次容量判断中选出 5 个 victim，而旧异步策略需要多轮释放和重新
调度。虽然最终 swap block 总量相同，decode batch 的时间分布已经不同。

扩展矩阵中的旧策略结果为：

| 场景 | 同步 tok/s | 旧安全异步 | 旧完全异步 | 完全异步相对同步 |
| --- | ---: | ---: | ---: | ---: |
| 12 请求，512/64 token | 198.076 | 196.660 | 196.653 | -0.72% |
| 12 请求，1024/128 token | 205.209 | 205.062 | 205.762 | +0.27% |
| 24 请求，512/64 token | 359.569 | 351.007 | 351.819 | -2.16% |
| 24 请求，1024/128 token | 387.673 | 355.800 | 366.082 | -5.57% |

并发增加后退化明显，而单独扩大 KV 数据量没有退化，说明瓶颈主要来自调度批次，而
不是 PCIe 传输量本身。已有微基准也显示 D2H 可达到约 24.1 GiB/s，接近 PCIe 4.0
x16 的实际有效上限。

## 优化设计

### 容量模型

遇到无法追加 KV block 的 decode 请求时，调度器计算：

```text
future_free   = 当前空闲 GPU blocks
future_demand = 候选请求下一轮需要新增的 blocks
```

随后从 running 队列尾部选择 victim。每选择一个 victim：

```text
future_free   += victim 当前占用的 GPU blocks
future_demand -= victim 自己下一轮需要的 block
```

当 `future_free >= future_demand` 时停止。这样选择的是能让其余候选请求在 event 完成
后组成完整 decode batch 的最少 victim 集合。

例如，24 个请求各占 2 个 blocks，且都需要追加 1 个 block：

```text
初始：future_free = 0，future_demand = 24
选择 8 个 victim 后：future_free = 16，future_demand = 16
```

所以一次换出 8 个请求即可。旧的过度抢占会接近换出全部请求，串行策略则要执行 8
轮 D2H；容量感知策略一次提交 8 个 victim。

### 边界处理

- victim 数量只增加到满足容量条件，不把整个 batch 全部驱逐。
- pending D2H 完成前，GPU blocks 仍不可分配。
- CPU swap 空间不足时沿用 recompute fallback，并使用实际 free block 数重新计算。
- 保留 `batched_async_preemption=False`，用于复现旧串行策略和执行消融实验。
- `unsafe_async_swap_out` 仍只用于研究完全重叠；安全异步是默认生产候选。

## 代码改动

- `Config` 增加 `batched_async_preemption`，默认启用。
- `Scheduler.preempt_for_decode_capacity` 实现最少 victim 容量计算。
- 异步 decode 路径把选出的 mappings 合并为一次 D2H 提交。
- benchmark 增加 `--serial-async-preemption`，可复现旧策略。
- 新增 `run_preemption_ablation.py`，在独立进程和轮换顺序下比较三种策略。
- 新增批量容量、串行消融和 pending block 生命周期测试。

## 实验方法

- GPU：NVIDIA A800 80GB PCIe，PCIe 4.0 x16
- 模型：Qwen3-1.7B
- KV cache：BF16，256 token/block，28 MiB/block
- 采样：argmax
- 每个方案运行 3 个独立进程
- 三次实验轮换方案执行顺序，降低温度和执行顺序偏差
- 原始 JSON、模型路径和 profiling 文件只保存在本地忽略目录

指标包括：

- 吞吐：所有生成 token / 端到端完成时间
- TTFT P95：首 token 延迟的 95 分位数
- TPOT P95：请求生成阶段平均每 token 时间的 95 分位数
- swap blocks、pending-only steps、scheduler steps
- 与同轮同步结果逐请求 token 完全匹配的数量

## 核心消融实验

最大压力场景：24 请求，输入 1024 token，输出 128 token，96 个 GPU blocks。

| 策略 | 吞吐 tok/s | 相对同步 | TTFT P95 ms | TPOT P95 ms | 输出匹配 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 同步 | 387.442 ± 4.894 | 基线 | 698.806 | 56.936 | 24/24 |
| 串行完全异步 | 363.442 ± 3.068 | -6.20% | 671.958 | 56.498 | 17/24 |
| 批量完全异步 | 388.255 ± 13.178 | +0.21% | 727.660 | 56.611 | 24/24 |

批量策略相对串行异步的吞吐提升为：

```text
388.255 / 363.442 - 1 = 6.83%
```

三种策略都换入和换出 20 个 blocks，因此收益不是减少传输数据量，而是恢复更大的
decode batch。消融实验的 TTFT 方差较大，所以延迟结论使用下面独立正式矩阵评估，
不使用该组 TTFT 均值宣称收益。

## 四组正式矩阵

### 吞吐

| 场景 | 同步 tok/s | 新安全异步 | 相对同步 | 新完全异步 | 相对同步 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 12 请求，512/64 token | 196.156 | 194.987 | -0.60% | 197.254 | +0.56% |
| 12 请求，1024/128 token | 204.403 | 202.973 | -0.70% | 204.402 | 0.00% |
| 24 请求，512/64 token | 356.678 | 359.194 | +0.71% | 357.594 | +0.26% |
| 24 请求，1024/128 token | 394.226 | 389.406 | -1.22% | 390.591 | -0.92% |

优化后四个场景的完全异步吞吐均位于同步的 ±1% 附近。旧策略在两个 24 并发场景
分别低 2.16% 和 5.57%，说明高并发退化已经基本消除。

### 延迟

| 场景 | 方案 | TTFT P95 ms | TPOT P95 ms |
| --- | --- | ---: | ---: |
| 12 请求，512/64 token | 同步 / 安全 / 完全 | 337.042 / 334.144 / 333.594 | 57.280 / 57.721 / 56.984 |
| 12 请求，1024/128 token | 同步 / 安全 / 完全 | 337.679 / 334.855 / 337.725 | 56.511 / 56.978 / 56.511 |
| 24 请求，512/64 token | 同步 / 安全 / 完全 | 669.119 / 667.196 / 672.735 | 59.129 / 58.728 / 58.946 |
| 24 请求，1024/128 token | 同步 / 安全 / 完全 | 669.688 / 679.403 / 672.609 | 56.085 / 56.770 / 56.643 |

优化后的延迟总体与同步接近。小规模完全异步的 TTFT P95 改善 1.02%、TPOT P95
改善 0.52%；最大压力下 TTFT 和 TPOT 分别回退 0.44% 和 1.00%。这些差异接近运行
波动，当前结论是消除了吞吐退化，而不是获得稳定的延迟加速。

### 正确性与资源状态

- 四组正式矩阵中，安全异步和完全异步均为全部请求逐 token 匹配同步结果。
- 同一压力点的同步、安全异步和完全异步 swap block 数完全一致。
- 16 个 CPU 调度测试全部通过。
- 2 个真实 CUDA event 集成测试全部通过。
- pending D2H 完成前，victim block 不会进入 free list。
- swap-in 完成前，请求不会回到 RUNNING。

输出匹配的恢复也有性能含义：容量感知策略恢复了与同步策略接近的 batch 组成，减少了
BF16 在不同 batch/kernel 路径下的数值漂移。逐 token 匹配仍不是并发系统内存安全的
唯一证据，block 生命周期测试和 correctness trace 才是主要正确性保证。

## 为什么方案有效

异步传输不只改变 memcpy 的执行方式，也改变资源何时对调度器可见。如果每次 event
只释放一个 victim，调度器会形成多个较小 decode batch；GPU kernel 启动和 batch
效率的损失可能大于传输重叠收益。

容量感知批量抢占把决策单位从“一个 victim”提升为“下一轮 decode 所需容量”。它没有
增加 swap 总量，也没有提前复用 pending block，只是让一次异步提交释放足以恢复有效
batch size 的容量。

## 局限与下一步

1. 实验使用单卡 A800 PCIe 和 Qwen3-1.7B，尚未覆盖其他模型结构和 NVLink。
2. 完全异步 D2H 仍保留诊断标记；生产默认更适合安全异步。
3. 四组结果每种运行 3 次，足以发现 5% 级退化，但不足以证明 1% 内的小收益。
4. 当前 demand 模型假设一次 decode 最多新增一个 block，符合现有 scheduler 行为。
5. 后续可加入 event 时长、每步 batch size 和 copy engine 利用率，进一步优化剩余的
   pending-only steps。

## 面试讲解框架

可以按下面的顺序在 3～5 分钟内介绍项目：

1. **问题**：GPU KV 不足时需要 CPU offload；异步 memcpy 能重叠计算，但高并发吞吐
   比同步低 5%～6%。
2. **观测**：swap 数据量没有增加，PCIe D2H 已接近实际带宽上限；退化随并发而不是
   单请求 KV 大小增长。
3. **根因**：为保护 pending blocks，异步调度器每个 event 只驱逐一个请求，导致多轮
   小 decode batch。
4. **方案**：建立 future free/demand 容量模型，一次选择刚好满足下一轮 batch 的最少
   victim，并合并 D2H 提交。
5. **结果**：同轮消融吞吐提升 6.83%，从同步的 -6.20% 提升到 +0.21%；四组正式
   矩阵均控制在同步 ±1% 左右；输出匹配恢复到 24/24。
6. **工程保证**：保留旧策略开关，16 个调度测试、2 个真实 CUDA event 测试、独立
   进程轮换顺序实验，原始数据和本地模型不进入仓库。

这个项目展示的重点不是单个 memcpy API，而是异步资源生命周期、容量规划、调度批次
与端到端指标之间的联系。
