# 同步、安全异步与完全异步 Swap 正式矩阵

## 实验设计

- 模型：Qwen3-1.7B。
- GPU：空闲的 NVIDIA A800 80GB。
- 请求：12 个，每个输入 512 tokens、输出 64 tokens。
- KV Cache 压力：32、24、20 个 GPU blocks。
- 方案：同步、安全异步、完全异步。
- 每组运行 3 次，每次使用独立进程。
- 三次重复采用不同执行顺序，减少时钟、温度和执行先后偏差。
- 使用严格 argmax，并逐请求比较同步基线的输出 tokens。

安全异步表示 D2H 等待完成、H2D 使用独立 stream。完全异步表示 D2H 和 H2D 都允许与其他请求计算重叠。

完全异步在压力增大后触发更多换入换出。新增传输和调度轮次超过了复制与计算重叠带来的收益，这是中度压力吞吐下降 12.97% 的主要系统层原因。

## 结论

1. 当前安全异步方案没有稳定提高吞吐。三档吞吐变化都在约 ±1% 内，和运行波动接近。
2. 安全方案在重度压力下降低 TTFT P95 约 6.83%，但 TPOT P95 增加约 1.68%，表现为首 token 与持续生成之间的权衡。
3. 当前完全异步方案不值得作为默认优化。它在中重度压力触发更多 swap，吞吐和 TPOT 明显变差。
4. 精确 token 一致性并不是 D2H 独有问题。32-block 安全异步也只有 11/12 请求与同步基线完全一致，说明 batch 组成、物理 block 分配或 kernel 执行轨迹变化都可能触发近似并列 logits 的 argmax 翻转。
5. 当前成果应描述为“异步 KV swap 正确性框架、性能测量工具和调度开销归因”。不能宣称已经获得稳定吞吐提升。

## 下一步优化方向

下一步不应继续简单扩大异步范围，而应减少异步状态造成的额外 swap：

- 为 swapping-in 请求预留恢复机会，避免刚恢复就再次被换出。
- 对比每个请求的 swap 次数，定位产生 22/22 blocks 传输的请求。
- 给调度器加入 swap cost 或最小驻留时间，抑制 ping-pong。
- 在 swap 次数与同步基线相同后，再判断传输和计算重叠本身是否有收益。
