# KV 数据量与并发扩展实验报告

## 目标

上一轮 12 并发、512 token 输入的实验中，异步方案与同步方案性能接近。本轮分别
扩大单请求 KV 数据量和并发请求数，观察异步传输何时产生收益，以及高压力下的性能
边界。

## 实验环境与方法

- 单张 NVIDIA A800 80GB PCIe
- Qwen3-1.7B，BF16 KV cache
- KV block size 为 256 token
- 每个 KV block 约 28 MiB
- argmax 采样
- 每种方案运行 3 个独立进程，并轮换执行顺序

模型共有 28 层、8 个 KV head，head dimension 为 128，因此单个 block 的大小为：

```text
K/V × layers × tokens × KV heads × head dimension × BF16 bytes
= 2 × 28 × 256 × 8 × 128 × 2
= 28 MiB
```

四个压力点都让初始 KV 基本占满指定的 GPU block，decode 追加新 block 时触发 swap。
原始 JSON 结果保存在本地忽略目录，仓库只保存汇总。

| 压力点 | 请求数 | 输入/输出 token | GPU blocks | 每方向 swap 数据量 |
| --- | ---: | ---: | ---: | ---: |
| 小规模基线 | 12 | 512 / 64 | 24 | 224 MiB |
| 大 KV | 12 | 1024 / 128 | 48 | 336 MiB |
| 高并发 | 24 | 512 / 64 | 48 | 448 MiB |
| 大 KV + 高并发 | 24 | 1024 / 128 | 96 | 560 MiB |

## 吞吐结果

| 压力点 | 同步 tok/s | 安全异步 tok/s | 相对同步 | 完全异步 tok/s | 相对同步 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 小规模基线 | 198.076 | 196.660 | -0.72% | 196.653 | -0.72% |
| 大 KV | 205.209 | 205.062 | -0.07% | 205.762 | +0.27% |
| 高并发 | 359.569 | 351.007 | -2.38% | 351.819 | -2.16% |
| 大 KV + 高并发 | 387.673 | 355.800 | -8.22% | 366.082 | -5.57% |

扩大 KV 数据量但保持 12 并发时，完全异步首次出现轻微吞吐正收益。提升到 24 并发
后，两种异步方案的总吞吐都下降；完全异步始终优于安全异步，但没有超过同步方案。

## 延迟结果

| 压力点 | 方案 | TTFT P95 ms | 相对同步 | TPOT P95 ms | 相对同步 |
| --- | --- | ---: | ---: | ---: | ---: |
| 小规模基线 | 同步 | 332.021 | — | 56.752 | — |
|  | 安全异步 | 328.339 | -1.11% | 56.816 | +0.11% |
|  | 完全异步 | 331.415 | -0.18% | 56.773 | +0.04% |
| 大 KV | 同步 | 371.034 | — | 56.036 | — |
|  | 安全异步 | 336.386 | -9.34% | 56.331 | +0.53% |
|  | 完全异步 | 340.460 | -8.24% | 56.117 | +0.15% |
| 高并发 | 同步 | 668.355 | — | 58.613 | — |
|  | 安全异步 | 662.950 | -0.81% | 59.440 | +1.41% |
|  | 完全异步 | 667.184 | -0.18% | 59.235 | +1.06% |
| 大 KV + 高并发 | 同步 | 685.806 | — | 57.026 | — |
|  | 安全异步 | 676.357 | -1.38% | 58.058 | +1.81% |
|  | 完全异步 | 671.111 | -2.14% | 56.134 | -1.56% |

组合压力下，完全异步虽然总吞吐低 5.57%，但 TTFT P95 和 TPOT P95 都优于同步。
这表示传输重叠改善了大部分请求的延迟，而请求尾部或整体完成时间仍拖慢了总吞吐。
后续需要记录请求完成时间分布和每步 batch size，才能定位吞吐损失集中在哪些请求和
调度阶段。

## Swap 与调度状态

| 压力点 | 方案 | swap in/out blocks | pending-only steps | scheduler steps |
| --- | --- | ---: | ---: | ---: |
| 小规模基线 | 同步 / 安全 / 完全 | 8/8 | 0 / 1 / 2 | 138 / 141 / 142 |
| 大 KV | 同步 / 安全 / 完全 | 12/12 | 0 / 1 / 2 | 266 / 268 / 269 |
| 高并发 | 同步 / 安全 / 完全 | 16/16 | 0 / 1 / 2 | 150 / 155 / 156 |
| 大 KV + 高并发 | 同步 / 安全 / 完全 | 20/20 | 0 / 1 / 2 | 278 / 281 / 282 |

同一压力点的三种方案具有完全相同的 swap block 数量，说明 pending D2H 过度抢占
没有复发。异步方案多出的调度步数来自 event 尚未完成时的空转或延后调度。

## 输出观察

- 大 KV、12 并发时，安全异步和完全异步均为 12/12 请求逐 token 匹配同步结果。
- 高并发时，异步方案有 16/24 或 17/24 请求逐 token 匹配同步结果。
- swap block 数量一致，已有 correctness trace 也没有发现 block 生命周期冲突。

高并发改变了 decode batch 的组成和浮点计算顺序，BF16 logits 接近 argmax 边界时会
产生不同 token。逐 token 匹配率在这里用于观察数值轨迹，不能单独证明或否定内存
正确性。

## 结论

扩大 KV 数据量本身对完全异步有利：在 12 并发、每方向传输 336 MiB 时，吞吐达到
同步方案的 100.27%，TTFT P95 改善 8.24%。

高并发是当前方案的性能边界。24 并发时，即使 swap 数量正确，异步方案的总吞吐仍
下降 2.16% 到 5.57%。组合压力下完全异步的延迟优于同步，说明重叠机制有效，但现有
调度方式没有把延迟收益转化为整体吞吐收益。

下一步应增加每步 batch size、event 等待时间和单请求完成时刻的追踪，区分三个候选
原因：异步 event 带来的调度气泡、swap 后 batch 变小，以及 memcpy 与模型计算争用
显存带宽。
